# 커피빵(CoffeeShout) 트러블슈팅 시나리오

> 요구사항에서 출발하여 문제를 직접 겪고, 해결하며 아키텍처를 성장시키는 과정.
> 각 단계는 "요구사항 → 구현 → 문제 발생 → 원인 분석 → 해결 → 검증"의 흐름을 따른다.

---

## 실험 환경

- Docker Compose로 WAS 2~3대 + Redis + Nginx(LB) 구성
- 부하 테스트: k6 또는 Artillery (WebSocket 지원)
- 모니터링: Redis MONITOR, WAS 로그, WebSocket 프레임 로그
- 장애 주입: `docker stop`, `docker pause`, `tc`(네트워크 지연)

---

## 시나리오 1. 스케일 아웃 — "서버 한 대로는 부족하다"

### 요구사항

> 동시 접속자가 늘어나고 있다.
> WAS를 여러 대 띄워서 수용할 수 있어야 한다.

### 구현

현재 구조: 단일 WAS, 게임 상태는 WAS 메모리에 저장.
WAS를 2대로 늘리고 Nginx로 라운드로빈 로드밸런싱을 건다.

### 문제 발생

**재현 방법:**
1. WAS 2대 기동
2. 같은 방에 유저 4명 접속
3. 유저A가 베팅

**현상:**
유저A의 베팅이 같은 WAS에 연결된 유저에게만 전달된다.
다른 WAS에 연결된 유저는 아무 변화 없음.

**로그 확인:**
```
[WAS-1] 유저A 베팅 처리 완료. 같은 서버 유저 2명에게 전송.
[WAS-2] ... (아무 로그 없음)
```

### 원인 분석

WebSocket 이벤트는 해당 WAS의 로컬 세션에만 브로드캐스트된다.
WAS 간에 이벤트를 전파하는 메커니즘이 없다.

```
[유저A, 유저B] → [WAS-1] ─── 베팅 이벤트 ───→ 유저A, 유저B만 수신
[유저C, 유저D] → [WAS-2] ─── ???? ───→ 유저C, 유저D는 모름
```

### 선택지 검토

**Sticky Session (같은 방 → 같은 서버):**
같은 방 유저를 같은 WAS로 몰면 전파 문제 자체가 사라진다.
하지만 이 선택의 대가를 시나리오 2에서 확인한다.

**이벤트 전파 (메시지 브로커):**
외부 메시지 브로커로 WAS 간 이벤트를 전파한다.
어떤 브로커를 쓸지는 시나리오 3에서 본격적으로 다룬다.

→ 우선 Sticky Session으로 빠르게 해결하고, 한계를 확인해본다.

### 해결 — 우선 Sticky Session으로 빠르게 해결

Nginx에서 방 ID 기반 라우팅을 설정한다.
WebSocket 핸드셰이크 시 쿼리 파라미터의 roomId를 기준으로 consistent hashing.

### 검증

- 같은 방 유저 4명이 모두 같은 WAS에 연결되는지 확인
- 베팅 이벤트가 전원에게 전달되는지 확인
- ✅ 동작 확인

### 남은 의문

> 이걸로 충분한가? 서버가 죽으면 어떻게 되지?

## 시나리오 2. 서버 장애 — "WAS 하나가 죽었는데 방이 통째로 날아갔다"

### 요구사항

> 서버 장애 상황에서도 진행 중인 게임이 유지되어야 한다.
> 운영 중 서버 한 대가 죽어도 서비스가 계속 동작해야 한다.

### 문제 발생

**재현 방법:**
1. Sticky Session 구조에서 WAS 2대 기동
2. 방 3개 생성, 각 방에 유저 4명 접속 (방 A, B는 WAS-1 / 방 C는 WAS-2)
3. 게임 진행 중 `docker stop was-1` 실행

**현상:**
- WAS-1에 연결된 방 A, B의 유저 8명 전원 WebSocket 끊김
- 유저들이 재접속 시도 → Nginx가 WAS-2로 보냄
- WAS-2에는 방 A, B의 게임 상태가 없음
- **방 A, B의 게임이 소멸됨. 진행 중이던 베팅 데이터 전부 유실.**

**로그 확인:**
```
[WAS-2] 유저A 재접속 요청. roomId=A. 해당 방 정보 없음. 404.
```

### 원인 분석

Sticky Session은 방과 서버가 1:1로 바인딩된다.
게임 상태가 WAS 메모리에만 존재하므로, 서버가 죽으면 상태도 사라진다.
다른 WAS로 재접속해도 상태를 복구할 방법이 없다.

```
[WAS-1 죽음] → 방 A, B의 메모리 상태 소멸
[WAS-2] → 방 A, B에 대한 정보 없음 → 복구 불가
```

**추가 문제 — 배포 시에도 동일한 문제:**
롤링 배포로 WAS-1을 내리면, 해당 서버의 모든 방이 중단된다.
무중단 배포가 사실상 불가능.

### 해결 — Sticky Session 폐기

**결정 근거:**
서버 장애 시 방이 전멸하는 구조는 실시간 게임 서비스에서 허용할 수 없다.
서버와 방의 결합을 끊어야 한다.

→ 이벤트 전파 메커니즘이 필요하다. 어떤 기술을 쓸 것인가?

## 시나리오 3. 메시지 브로커 선택 — "이벤트를 어떻게 전파할 것인가"

### 요구사항

> Sticky Session을 버렸다. 유저가 아무 WAS에나 접속할 수 있다.
> 같은 방 유저가 다른 WAS에 있어도, 이벤트가 전달되어야 한다.
> 이벤트 전파 기술을 선택해야 한다.

### 선택지 정리

이벤트를 WAS 간에 전파하는 기술 선택지:

| | Redis Pub/Sub | Redis Stream | Kafka |
|---|---|---|---|
| 메시지 보관 | ✗ (fire-and-forget) | ✓ (로그 보관) | ✓ (로그 보관) |
| 순서 보장 | 단일 채널 내 ✓ | ✓ | 파티션 내 ✓ |
| 유실 가능성 | 있음 | 없음 (ACK 기반) | 없음 (ACK 기반) |
| 컨슈머 관리 | 불필요 | 필요 (컨슈머 그룹, MAXLEN) | 필요 (컨슈머 그룹, 오프셋) |
| 인프라 비용 | Redis만 있으면 됨 | Redis만 있으면 됨 | Kafka 클러스터 별도 필요 |
| 지연 | 극도로 낮음 | 낮음 | 낮음 (배치 시 증가) |

### 첫 번째 판단 — "메시지를 보관해야 하는가?"

Stream과 Kafka의 핵심 강점은 **메시지 보관**이다.
메시지를 보관하면 컨슈머가 놓친 메시지를 나중에 다시 읽을 수 있다.
이것이 필요한가?

**메시지 보관이 필요한 경우:**
- WAS가 죽었다 살아났을 때, 놓친 이벤트를 리플레이해서 상태를 복구해야 하는 경우
- 즉, **이벤트가 상태 복원의 유일한 수단**인 경우
- 즉, **SSOT가 WAS 메모리**에 있는 경우

이 경우 리플레이 복구의 문제:
- 서비스 트랜잭션의 시작점 메시지부터 전부 받아와야 정합성이 맞음
- Stream/Kafka에 해당 메시지가 이미 정리(MAXLEN/retention)되어 없을 수 있음
- 트랜잭션과 무관한 메시지까지 전부 처리해야 할 수 있음
- 리플레이 중 에러 발생 시 예외 케이스 폭발
  → **복구 로직이 서비스 로직보다 복잡해지는 역전 현상**

### 핵심 질문 전환 — "SSOT를 어디에 둘 것인가?"

메시지 브로커를 고르기 전에, 이 질문이 먼저다.

**게임 상태의 원본(SSOT)을 Redis에 두면?**
- WAS가 죽어도 상태는 Redis에 살아있음
- 복구 = Redis에서 최신 상태 읽기. 끝.
- 이벤트 리플레이가 필요 없음
- **메시지 보관이 필요 없음**
- 메시지 브로커는 "상태가 바뀌었다"는 **알림(notification)** 역할만 하면 됨

**SSOT가 Redis에 있으면:**
- Stream의 메시지 보관 → 불필요한 기능. 오히려 컨슈머 그룹, MAXLEN 관리 비용만 추가.
- Kafka의 메시지 보관 → 마찬가지로 불필요. 게다가 별도 클러스터 인프라까지 필요.
- Pub/Sub의 fire-and-forget → **문제가 아니라 오히려 적합.** 유실되면 Redis에서 읽으면 됨.

### 의사결정

**→ Redis를 게임 상태의 SSOT로 사용한다.**
**→ 이벤트 전파는 Redis Pub/Sub을 사용한다.**
**→ MySQL은 게임 결과 영속 저장용으로만 사용한다.**

**Redis SSOT 근거:**
- 실시간성 요구 충족 (인메모리)
- 원자적 연산으로 동시성 제어 가능 (Lua 스크립트)
- 서버 장애 시 상태 보존
- MySQL은 게임 상태 같은 고빈도 쓰기에 부적합 (락 경합, 레이턴시)

**Pub/Sub 근거:**
- SSOT가 Redis에 있으므로 메시지 보관 불필요 → Stream/Kafka의 핵심 강점이 쓸모없음
- 컨슈머 관리 불필요 → 운영 복잡도 최소
- 이미 Redis를 쓰고 있으므로 추가 인프라 없음
- 유실 대응은 시퀀스 번호 + 풀 스테이트 싱크로 해결 (시나리오 5에서 다룸)

**핵심 인사이트:**
> **"Stream/Kafka가 필요한 구조 자체가 설계 문제다."**
> 메시지 보관이 필요하다는 것은 SSOT가 올바른 위치에 없다는 신호다.
> SSOT를 Redis로 옮기면 메시지 브로커의 역할이 알림으로 축소되고,
> 가장 단순한 Pub/Sub이 최적의 선택이 된다.

### 구현

1. 게임 상태를 Redis Hash에 저장: `room:{roomId}` → 방 상태, 참가자, 베팅 정보, 시퀀스 번호
2. 상태 변경을 Lua 스크립트로 원자적 처리:
    - 상태 검증 + 변경 + 시퀀스 번호 증가 + PUBLISH를 하나의 원자적 연산으로
3. Nginx: 단순 라운드로빈
4. WAS: 방에 첫 유저 접속 시 `room:{roomId}` 채널 subscribe, 마지막 유저 퇴장 시 unsubscribe

**이벤트 흐름:**
```
유저A 베팅 요청
  → [WAS-1] Redis Lua 스크립트 실행
  → [Redis] 상태 변경 + seq++ + PUBLISH (원자적)
  → [Pub/Sub] → [WAS-2] 이벤트 수신 → 유저B에게 WebSocket 전송
```

### 검증

**장애 복구 테스트:**
1. 방 A에서 게임 진행 (베팅 5건)
2. `docker stop was-1`
3. WAS-1의 유저들이 WAS-2에 재접속
4. WAS-2가 Redis에서 방 A의 최신 상태를 조회하여 클라이언트에 전송
5. ✅ 게임 상태 복구 완료. 베팅 5건 모두 보존.

**동시 쓰기 테스트:**
1. 슬롯 1개 남은 상태에서 유저A(WAS-1)와 유저B(WAS-2)가 동시 베팅
2. Lua 스크립트가 Redis 단에서 직렬 처리
3. 먼저 도착한 요청만 성공, 나중 요청은 INVALID_STATE 반환
4. ✅ 정합성 유지

## 시나리오 4. 서버 장애 시 재접속 — "끊기고 다시 들어왔는데 게임이 이어진다"

### 요구사항

> WAS가 죽으면 해당 서버의 모든 클라이언트 WebSocket이 끊긴다.
> 클라이언트가 다른 WAS에 재접속했을 때, 게임이 이어져야 한다.

### 구현

**클라이언트 재접속 전략:**
```
1. WebSocket 연결 끊김 감지
2. 지수 백오프(Exponential Backoff)로 재접속 시도
   - 1초 → 2초 → 4초 → 8초 (최대 30초)
   - jitter 추가로 thundering herd 방지
3. 로드밸런서가 살아있는 아무 WAS에 연결
4. 재접속 시 클라이언트가 보내는 정보:
   - roomId
   - 마지막으로 받은 시퀀스 번호 (lastSeq)
```

**WAS의 재접속 처리:**
```
1. 클라이언트로부터 roomId, lastSeq 수신
2. Redis에서 해당 방의 현재 상태 + 현재 seq 조회
3. 클라이언트에게 풀 스테이트 전송 (현재 게임 상태 전체)
4. 해당 방 채널을 아직 subscribe 하지 않았으면 subscribe
5. 이후 정상적인 이벤트 흐름으로 복귀
```

### 문제 발생 — Thundering Herd

**재현 방법:**
1. WAS 3대 기동. WAS-1에 유저 500명 연결
2. `docker stop was-1` 실행
3. 500명이 동시에 WAS-2, WAS-3으로 재접속 시도

**현상:**
- WAS-2, WAS-3에 250명씩 WebSocket 핸드셰이크 요청 폭주
- 각 유저가 재접속 시 풀 스테이트 싱크 요청 → Redis에 HGETALL 250건 동시 요청
- **같은 방 유저 4명이 거의 동시에 풀 스테이트 요청 → 같은 데이터를 4번 읽기**
- Redis CPU 급등, 일부 요청 타임아웃

**로그 확인:**
```
[WAS-2] 재접속 150건 수신. 풀 스테이트 싱크 150건 실행 중...
[WAS-2] Redis 응답 지연: HGETALL room:37 → 800ms (평소 2ms)
[WAS-2] 일부 클라이언트 타임아웃으로 재접속 실패
```

### 원인 분석

500명이 거의 동시에 재접속하면서 Redis에 부하가 집중된다.
특히 같은 방의 유저 여러 명이 동시에 풀 스테이트를 요청하면,
동일한 데이터를 여러 번 읽는 비효율 발생.

### 해결 — 3단계 방어

**Step 1: 클라이언트 측 — Jitter가 있는 지수 백오프**
```
재접속 대기 시간 = min(baseDelay * 2^attempt, maxDelay) + random(0, jitter)

예시:
  1차 시도: 1초 + random(0, 500ms)
  2차 시도: 2초 + random(0, 500ms)
  3차 시도: 4초 + random(0, 500ms)
  최대: 30초
```
jitter로 재접속 시점을 분산시켜 동시 요청을 줄인다.

**Step 2: WAS 측 — Request Coalescing (요청 병합)**
같은 방에 대한 풀 스테이트 요청이 짧은 시간 내에 여러 건 들어오면,
Redis에는 **1번만 조회**하고 결과를 모든 요청자에게 공유한다.

```
유저A 재접속 → room:37 풀 싱크 요청 → Redis 조회 시작
유저B 재접속 → room:37 풀 싱크 요청 → 이미 조회 중 → 대기열에 추가
유저C 재접속 → room:37 풀 싱크 요청 → 이미 조회 중 → 대기열에 추가
Redis 응답 도착 → 유저A, B, C 모두에게 동일한 결과 전송
```

구현: `ConcurrentHashMap<roomId, CompletableFuture<GameState>>` 패턴

**Step 3: 연결 수 제한 — 점진적 수용**
WAS 레벨에서 초당 재접속 수용 수를 제한한다.
초과 요청은 503으로 응답 → 클라이언트가 백오프 후 재시도.

### 검증

**Thundering herd 시뮬레이션:**
1. WAS-1에 500명 → `docker stop was-1`
2. 방어 적용 전: Redis CPU 95%, 재접속 실패율 30%
3. 방어 적용 후: Redis CPU 40%, 재접속 실패율 0%, 전체 복구 시간 5초 이내
4. ✅ Request coalescing으로 Redis 조회 수가 500건 → 80건(방 수)으로 감소

## 시나리오 5. 메시지 유실 — "Pub/Sub 이벤트가 중간에 사라졌다"

### 요구사항

> Redis Pub/Sub으로 이벤트를 전파하고 있다.
> 이벤트가 유실되더라도 클라이언트의 게임 화면이 정확해야 한다.

### 문제 발생

**재현 방법:**
1. WAS 2대 기동, 방 A에 유저 4명
2. WAS-2의 Redis 연결을 순간적으로 끊었다 복구 (`docker pause redis` → 2초 후 `docker unpause`)
3. 그 2초 사이에 WAS-1에서 베팅 이벤트 3건 발생

**현상:**
- WAS-1: 이벤트 3건 정상 처리 및 publish
- WAS-2: Redis 연결이 끊겨 있던 2초간의 이벤트 3건을 수신하지 못함
- WAS-2에 연결된 유저의 화면이 **3건 뒤처진 상태**로 멈춤

**로그 확인:**
```
[WAS-2] Redis 연결 끊김 감지. 재연결 시도...
[WAS-2] Redis 재연결 성공. subscribe 복구.
[WAS-2] 다음 수신 이벤트 seq=8. 마지막 처리 seq=4. 갭 감지: 5,6,7 유실.
```

### 원인 분석

Redis Pub/Sub은 fire-and-forget이다.
구독자가 연결이 끊겨 있으면 그 사이의 메시지는 사라진다. 버퍼에 보관하지 않는다.

이것은 Pub/Sub의 버그가 아니라 **설계상 의도된 동작**이다.
Pub/Sub은 "지금 듣고 있는 사람에게만 전달"하는 모델.

시나리오 3에서 "Pub/Sub 유실은 SSOT에서 다시 읽으면 된다"고 판단했다.
이제 그 메커니즘을 구현한다.

### 해결 — 시퀀스 번호 기반 유실 감지 + 풀 스테이트 싱크

**Step 1: 시퀀스 번호는 이미 있다**
시나리오 3에서 Lua 스크립트로 모든 이벤트에 시퀀스 번호를 부여하고 있다.
WAS는 방마다 마지막으로 처리한 시퀀스 번호를 기억한다.

**Step 2: 갭 감지 로직 추가**
```
이벤트 수신 시:
  if (received.seq == expected.seq)  → 정상 처리, expected++
  if (received.seq > expected.seq)   → 갭 감지 → 풀 스테이트 싱크 트리거
  if (received.seq < expected.seq)   → 이미 처리한 이벤트, 무시
```

**Step 3: 풀 스테이트 싱크**
갭을 감지하면, **빠진 이벤트를 찾는 것이 아니라** Redis에서 현재 게임 상태를 통째로 가져온다.
```
1. Redis HGETALL room:{roomId} → 전체 게임 상태 + 현재 seq
2. WAS 로컬 상태를 덮어쓰기
3. expected.seq를 현재 seq + 1로 갱신
4. 해당 방의 모든 클라이언트에게 풀 스테이트 전송
```

**왜 빠진 이벤트를 리플레이하지 않는가:**
- 빠진 이벤트를 보관하려면 Stream이 필요 → 관리 비용 발생
- SSOT가 Redis에 있으므로, 최신 상태를 읽는 것이 가장 단순하고 확실
- 게임 방 하나의 상태 크기가 작으므로 (4~10명의 베팅 정보) 풀 싱크 비용이 저렴
- **"유실 시 리플레이"가 아니라 "유실 시 최신 스냅샷"** 전략

### 검증

**유실 재현 테스트:**
1. WAS-2의 Redis 연결을 2초간 끊기
2. 그 사이 이벤트 3건 발생
3. 재연결 후 WAS-2가 갭 감지 → 풀 스테이트 싱크 실행
4. WAS-2의 유저들에게 최신 상태 전송
5. ✅ 유저 화면이 최신 상태로 복구됨

**빈번한 유실 시 성능 테스트:**
1. 1초에 1번씩 Redis 연결 끊었다 복구 반복
2. 매번 풀 스테이트 싱크 발생
3. Redis 부하 모니터링 → 방 상태가 작으므로 HGETALL 비용 미미
4. ✅ 초당 수회 풀 싱크에도 Redis CPU 1% 미만

## 시나리오 6. 순서 역전 — "베팅 취소가 베팅보다 먼저 처리됐다"

### 요구사항

> Pub/Sub 이벤트의 처리 순서가 보장되어야 한다.
> 유저의 행동이 시간 순서대로 반영되어야 한다.

### 문제 발생

**재현 방법:**
1. WAS 2대 기동, 방 A에 유저 4명
2. 유저A가 빠르게 "베팅 → 베팅 취소"를 연속으로 요청
3. WAS-2에서 이벤트 처리

**현상:**
Redis Pub/Sub 자체는 단일 채널 내 순서를 보장한다 (Redis 싱글 스레드).
하지만 WAS-2가 이벤트를 수신한 후, **멀티스레드로 처리**하면서 순서가 꼬인다.

```
[WAS-2 수신 순서] seq=1: BET_PLACED → seq=2: BET_CANCELLED (정상)
[WAS-2 처리 순서] 스레드A가 seq=2 먼저 처리 완료 → 스레드B가 seq=1 처리
결과: 베팅 취소 후 베팅이 적용됨 → 취소가 씹힘
```

### 원인 분석

Pub/Sub 수신은 단일 스레드에서 순서대로 이루어진다.
하지만 수신한 이벤트를 **비동기로 처리 스레드에 넘기는 과정**에서
스레드 스케줄링에 의해 처리 완료 순서가 뒤바뀔 수 있다.

특히 이벤트마다 처리 시간이 다르면 (예: 베팅 검증은 빠르고, 취소는 환불 로직이 있어서 느리면)
나중에 도착한 이벤트가 먼저 처리 완료될 수 있다.

### 해결 — 방 단위 액터 모델

**핵심 아이디어:**
각 방마다 하나의 "액터"를 두고, 해당 방의 모든 이벤트를 **순차적으로** 처리한다.
방 간에는 독립적으로 병렬 처리하여 전체 처리량은 유지한다.

**구현:**
```
[Pub/Sub 수신 스레드 (단일)]
  │
  ├── room:A 이벤트 → [Room-A 큐] → [Room-A 전용 스레드] → 순차 처리
  ├── room:B 이벤트 → [Room-B 큐] → [Room-B 전용 스레드] → 순차 처리
  └── room:C 이벤트 → [Room-C 큐] → [Room-C 전용 스레드] → 순차 처리
```

**Java 구현 방식:**
- 방마다 `ConcurrentLinkedQueue` + 단일 스레드 처리 루프
- 또는 방마다 `SingleThreadExecutor`에 task 제출
- 이벤트 수신 → roomId로 해당 방의 큐에 offer → 액터가 poll하며 순차 처리

**액터 내부에서 시퀀스 검증:**
```
poll한 이벤트의 seq 확인:
  seq == expected → 처리, expected++
  seq > expected  → 갭 감지 → 풀 스테이트 싱크
  seq < expected  → 무시 (중복)
```

액터 내부는 단일 스레드이므로 시퀀스 검증에 동기화가 필요 없다.

### 검증

**순서 역전 테스트:**
1. 유저A가 1ms 간격으로 "베팅 → 취소 → 재베팅" 연속 요청
2. WAS-2에서 이벤트 처리 순서 로그 확인
3. ✅ seq 순서대로 처리됨. 취소가 베팅 전에 처리되는 현상 제거.

**병렬성 테스트:**
1. 방 100개, 각 방에 초당 10건 이벤트
2. 방 간 병렬 처리로 전체 처리량 확인
3. ✅ 단일 스레드 대비 처리량 30배 이상 (방 수에 비례)

## 시나리오 7. 분산 스케줄링 — "베팅 마감 타이머가 서버랑 같이 죽었다"

### 요구사항

> 게임에는 시간 기반 로직이 있다.
> - 베팅 마감 타이머 (30초 후 자동 마감)
> - 게임 결과 공개 딜레이 (5초 후 결과 오픈)
> - 비활성 방 정리 (10분간 활동 없으면 방 종료)
> - 재접속 대기 (grace period: 유저가 30초 내 재접속 안 하면 탈퇴 처리)
>
> 분산 환경에서 이 타이머들이 안정적으로 동작해야 한다.

### 7-1. 첫 번째 시도 — WAS 메모리 타이머

#### 구현

가장 직관적인 방법. WAS에서 `ScheduledExecutorService`로 타이머를 건다.

```java
scheduler.schedule(() -> {
    closeBetting(roomId);
}, 30, TimeUnit.SECONDS);
```

#### 문제 발생

**재현 방법:**
1. 방 A에서 베팅 시작. WAS-1이 30초 타이머 설정.
2. 15초 경과 시점에 `docker stop was-1`
3. 유저들이 WAS-2에 재접속

**현상:**
- WAS-1의 타이머가 서버와 함께 소멸
- WAS-2는 방 A의 베팅 마감 타이머가 있었다는 것을 모름
- **베팅이 영원히 마감되지 않음**

**로그 확인:**
```
[WAS-2] 유저들 재접속 완료. 방 A 풀 스테이트 싱크 성공.
[WAS-2] 방 A 상태: BETTING. 마감 타이머? 없음.
... (30초, 1분, 5분 경과)
[WAS-2] 방 A 상태: 여전히 BETTING. 아무도 마감 안 함.
```

#### 원인 분석

타이머도 상태다. WAS 메모리에 있는 타이머는 서버가 죽으면 사라진다.
게임 상태를 Redis SSOT로 옮긴 것과 같은 이유로, **스케줄도 WAS 메모리에 두면 안 된다.**

추가 문제: 타이머가 WAS에 있으면, 같은 방을 여러 WAS가 구독하고 있을 때 **어떤 WAS가 타이머를 책임지는가**도 모호하다. 모든 WAS가 타이머를 걸면 중복 실행된다.

### 7-2. 두 번째 시도 — Redis Keyspace Notification

#### 구현

타이머를 Redis에 TTL 키로 등록하고, 만료 시 Keyspace Notification으로 이벤트를 받는다.

```
SET room:A:bet_deadline "" EX 30
→ 30초 후 Redis에서 expired 이벤트 발생
→ WAS가 __keyevent@0__:expired 채널에서 수신
```

이렇게 하면 타이머가 Redis에 있으므로 WAS 장애에 영향 없다.

#### 문제 발생 — 중복 실행

**재현 방법:**
1. WAS 3대 모두 `__keyevent@0__:expired` 채널을 subscribe
2. 방 A의 베팅 마감 키 만료

**현상:**
- 3대 모두 expired 이벤트를 수신
- 3대 모두 `closeBetting(roomA)` 실행
- **마감 처리가 3번 실행됨**

**로그 확인:**
```
[WAS-1] room:A:bet_deadline expired. 마감 처리 실행.
[WAS-2] room:A:bet_deadline expired. 마감 처리 실행.
[WAS-3] room:A:bet_deadline expired. 마감 처리 실행.
```

#### 해결 시도 — 분산 락으로 중복 방지

expired 이벤트를 수신한 WAS가 Redis 분산 락을 먼저 잡고, 락을 잡은 WAS만 실행.

```
SETNX room:A:bet_deadline:lock <wasId> EX 5
→ 성공하면 마감 처리 실행
→ 실패하면 다른 WAS가 처리 중이므로 무시
```

#### 문제 발생 — 유실 시 아무도 실행 안 함

**재현 방법:**
1. 키 만료 시점에 모든 WAS의 Redis 연결이 순간 끊김 (네트워크 지터)
2. 재연결 후 expired 이벤트는 이미 사라짐

**현상:**
- Keyspace Notification도 **Pub/Sub 기반**이므로 fire-and-forget
- 3대 모두 이벤트를 놓침
- **베팅이 영원히 마감되지 않음**

**로그 확인:**
```
[WAS-1] Redis 재연결 완료. subscribe 복구.
[WAS-2] Redis 재연결 완료. subscribe 복구.
[WAS-3] Redis 재연결 완료. subscribe 복구.
... (expired 이벤트는 이미 발행됨. 아무도 못 받음.)
```

#### 추가 문제 — TTL 만료 시점 부정확

Redis의 key 만료는 두 가지 방식으로 동작한다:
- **Lazy expiration:** 키에 접근할 때 만료 확인 → 접근 안 하면 만료 이벤트도 안 남
- **Active expiration:** Redis가 주기적으로 샘플링하여 만료 키 정리 → 정확한 시점 보장 안 됨

Redis 공식 문서에도 "Keyspace Notification으로 reliable한 타이머를 구현하지 말라"고 명시되어 있다.

#### 원인 분석 정리

Keyspace Notification의 근본 문제:
1. Pub/Sub 기반이므로 유실 가능 → 아무도 실행 안 하는 케이스 발생
2. 모든 WAS가 수신 → 중복 실행. 락으로 해결 가능하지만 유실과 결합하면 안전하지 않음
3. TTL 만료 시점이 정확하지 않음
4. **push 모델의 한계:** 알림을 놓치면 복구 방법이 없음

### 7-3. 최종 해결 — Sorted Set + 폴링

#### 핵심 아이디어

push가 아니라 **pull** 모델로 바꾼다.
스케줄을 Redis Sorted Set에 등록하고, WAS가 주기적으로 폴링해서 실행 시각이 지난 작업을 가져간다.

push 모델(Keyspace Notification)은 알림을 놓치면 끝이지만,
pull 모델(폴링)은 **데이터가 Redis에 남아있으므로 누군가가 가져갈 때까지 사라지지 않는다.**

#### 구현

**스케줄 등록:**
```
ZADD schedules <실행시각_timestamp> "room:A:close_betting"
ZADD schedules <실행시각_timestamp> "room:B:reveal_result"
```
score = 실행할 시각의 Unix timestamp

**폴링 + 원자적 소비 (Lua 스크립트):**
```lua
-- 실행 시각이 지난 작업을 최대 10개 가져오고 동시에 삭제
local now = tonumber(ARGV[1])
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', now, 'LIMIT', 0, 10)

if #tasks == 0 then
  return {}
end

-- 가져온 작업을 Sorted Set에서 제거 (다른 WAS가 중복으로 가져가지 못하게)
for i, task in ipairs(tasks) do
  redis.call('ZREM', KEYS[1], task)
end

return tasks
```

**핵심:** `ZRANGEBYSCORE` + `ZREM`을 Lua로 원자적으로 실행.
한 WAS가 가져간 작업은 즉시 삭제되므로 다른 WAS가 중복으로 가져갈 수 없다.
분산 락이 필요 없다.

**WAS의 폴링 루프:**
```java
@Scheduled(fixedRate = 1000)  // 1초마다
public void pollSchedules() {
    List<String> tasks = redis.executeLua(POLL_SCRIPT, now());
    for (String task : tasks) {
        execute(task);  // room:A:close_betting → closeBetting("A")
    }
}
```

**스케줄 등록 시점:**
게임 상태 변경 Lua 스크립트 안에서 스케줄도 함께 등록한다.
```lua
-- 베팅 시작 처리 Lua 스크립트 내부
redis.call('HSET', room_key, 'state', 'BETTING')
redis.call('ZADD', 'schedules', now + 30, 'room:' .. room_id .. ':close_betting')
redis.call('PUBLISH', channel, event)
```
상태 변경 + 스케줄 등록 + 이벤트 발행이 하나의 원자적 연산.

#### 검증

**WAS 장애 테스트:**
1. WAS-1이 방 A의 베팅 시작 처리 → Sorted Set에 30초 후 마감 스케줄 등록
2. 15초 후 `docker stop was-1`
3. 스케줄은 Redis Sorted Set에 남아있음
4. 30초 후 WAS-2 또는 WAS-3의 폴링이 해당 스케줄을 가져감
5. ✅ 마감 정상 실행

**중복 실행 테스트:**
1. WAS 3대가 동시에 폴링
2. Lua 스크립트의 원자적 ZRANGEBYSCORE + ZREM으로 하나의 WAS만 작업 획득
3. ✅ 마감 1회만 실행

**전체 유실 테스트 (Keyspace Notification과의 비교):**
1. 스케줄 실행 시각에 모든 WAS의 Redis 연결이 순간 끊김
2. 재연결 후 다음 폴링 주기에 밀린 스케줄을 모두 가져감
3. ✅ 유실 없음. 데이터가 Sorted Set에 남아있었으므로.

#### 트레이드오프 정리

| | WAS 메모리 타이머 | Keyspace Notification | Sorted Set + 폴링 |
|---|---|---|---|
| WAS 장애 시 | ✗ 타이머 소멸 | △ 유실 가능 | ✓ 스케줄 보존 |
| 중복 실행 | 모호 | 락 필요 | Lua 원자 연산 |
| 유실 가능성 | 높음 | 있음 (pub/sub) | 없음 (pull 모델) |
| 시각 정확도 | 정확 | 부정확 (lazy exp.) | 폴링 주기만큼 오차 |
| 관리 비용 | 없음 | 중 | 저 |
| 기존 패턴 일관성 | ✗ | △ | ✓ (Redis + Lua) |

#### 폴링 지연에 대해

1초 폴링이면 최대 1초 지연이 생긴다.
게임 타이머에서 1초 오차는 체감할 수 없는 수준이다.
만약 100ms 정밀도가 필요하다면 폴링 주기를 줄이면 되지만,
WAS 3대 × 초당 10회 = 초당 30건 ZRANGEBYSCORE는 Redis에 무시할 수 있는 부하.

## 시나리오 8. 클라이언트 메시지 중복 — "베팅이 두 번 들어갔다"

### 요구사항

> 네트워크 불안정으로 클라이언트의 요청이 중복 전송될 수 있다.
> 같은 요청이 여러 번 도착해도 한 번만 처리되어야 한다.

### 문제 발생

**재현 방법:**
1. 유저A가 베팅 요청 전송
2. WAS-1이 요청 수신 → Redis에 상태 변경 완료
3. 하지만 WebSocket ACK가 클라이언트에 도달하기 전에 네트워크 지연
4. 클라이언트가 타임아웃으로 같은 요청을 재전송
5. WAS-1이 같은 베팅을 또 처리

**현상:**
- 유저A의 5,000원 베팅이 두 번 처리됨
- 게임 상태에 유저A가 10,000원 베팅한 것으로 기록

### 원인 분석

클라이언트의 재전송은 정당한 행동이다 (응답을 못 받았으니).
문제는 서버가 **이미 처리한 요청과 새 요청을 구분하지 못하는 것**.

### 해결 — 멱등성 키 (Idempotency Key)

**클라이언트:**
모든 요청에 고유한 requestId를 포함한다.
```json
{
  "type": "BET",
  "amount": 5000,
  "requestId": "uuid-xxx-yyy"
}
```
재전송 시에도 **같은 requestId**를 사용한다.

**서버 (Lua 스크립트):**
```lua
-- 멱등성 체크
local processed = redis.call('SISMEMBER', room_key .. ':processed', request_id)
if processed == 1 then
  -- 이미 처리된 요청. 기존 결과 반환.
  return redis.call('HGET', room_key, 'last_result:' .. request_id)
end

-- 베팅 처리
-- ...

-- 처리 완료 기록
redis.call('SADD', room_key .. ':processed', request_id)
redis.call('HSET', room_key, 'last_result:' .. request_id, result)
-- TTL 설정으로 오래된 기록 자동 정리
redis.call('EXPIRE', room_key .. ':processed', 300)
```

### 검증

**중복 요청 테스트:**
1. 같은 requestId로 베팅 요청 5번 전송
2. 첫 번째만 처리, 나머지 4건은 기존 결과 반환
3. ✅ 베팅 금액 정확히 5,000원 (중복 처리 없음)

## 시나리오 9. 배포 — "무중단으로 서버를 교체해야 한다"

### 요구사항

> 새 버전을 배포할 때 진행 중인 게임이 중단되면 안 된다.
> 유저가 배포 사실을 체감하지 못해야 한다.

### 동작 확인

이전 시나리오들에서 만든 아키텍처가 무중단 배포를 자연스럽게 지원하는지 확인한다.

**배포 절차:**
```
1. WAS-1에 새 연결 수신 중단 (Nginx에서 WAS-1을 upstream에서 제거)
2. WAS-1의 기존 연결에 "서버 교체 예정" 메시지 전송 (선택)
3. 일정 시간(graceful shutdown period) 대기
4. WAS-1 종료
   → 유저들 WebSocket 끊김
   → 클라이언트 지수 백오프 + jitter로 재접속 (시나리오 4)
   → 다른 WAS에 연결
   → Redis에서 풀 스테이트 싱크 (시나리오 5)
   → 게임 계속
5. WAS-1 새 버전으로 기동
6. Nginx에 WAS-1 재추가
7. WAS-2, WAS-3에 대해 반복
```

**스케줄링도 안전:**
- WAS-1이 내려가도 스케줄은 Redis Sorted Set에 남아있음 (시나리오 7)
- 다른 WAS의 폴링이 밀린 스케줄을 가져감
- ✅ 타이머 소멸 없음

### 검증

- 롤링 배포 중 WebSocket 메시지 유실 건수 확인
- 풀 스테이트 싱크로 복구되므로 유실 허용 (수 초 내 복구)
- 스케줄 실행 누락 여부 확인
- ✅ 유저 체감 끊김: 1~3초 (재접속 시간)
- ✅ 게임 상태, 스케줄 모두 보존

## 최종 아키텍처

```
                      [Nginx - L7 Load Balancer]
                      (Round Robin, no sticky)
                     /           |           \
               [WAS-1]       [WAS-2]       [WAS-3]
               │                │                │
               ├─ WebSocket     ├─ WebSocket     ├─ WebSocket
               │  Session Mgr   │  Session Mgr   │  Session Mgr
               │                │                │
               ├─ Room Actors   ├─ Room Actors   ├─ Room Actors
               │  (순서 보장)    │  (순서 보장)    │  (순서 보장)
               │                │                │
               ├─ Seq 갭 감지    ├─ Seq 갭 감지    ├─ Seq 갭 감지
               │                │                │
               ├─ Request       ├─ Request       ├─ Request
               │  Coalescing    │  Coalescing    │  Coalescing
               │                │                │
               └─ Schedule      └─ Schedule      └─ Schedule
                  Poller (1s)      Poller (1s)      Poller (1s)
                     \           |           /
                      ↕          ↕          ↕
                 [Redis - 단일 진실 공급원(SSOT)]
                 ├── Hash: room:{id}
                 │   ├── 게임 상태 (방 정보, 참가자, 베팅)
                 │   ├── 시퀀스 번호 (seq)
                 │   └── 멱등성 키 (processed set)
                 ├── Sorted Set: schedules
                 │   └── score=실행시각, member=작업식별자

                 │   └── 변경 알림 (notification only)
                 ├── Lua Scripts
                 │   ├── 상태 변경 + seq++ + PUBLISH + 스케줄 등록 (원자적)
                 │   └── 스케줄 폴링 + 소비 (원자적)
                 └── Sentinel (고가용성)

                       [MySQL]
                   (게임 결과 영속 저장)
```

## 시나리오별 아키텍처 성장 요약

| # | 시나리오 | 문제 | 해결 | 아키텍처 변화 |
|---|---|---|---|---|
| 1 | 스케일 아웃 | 다른 WAS 유저에게 이벤트 안 감 | Sticky Session (임시) | 단일 WAS → 다중 WAS |
| 2 | 서버 장애 | Sticky Session에서 방 전멸 | Sticky Session 폐기 결정 | 이벤트 전파 필요성 확인 |
| 3 | 브로커 선택 | Stream/Kafka vs Pub/Sub | SSOT 결정이 선행 → Redis SSOT → Pub/Sub | Redis SSOT + Pub/Sub + Lua |
| 4 | 재접속 | Thundering herd | Jitter + Request Coalescing | 클라이언트/서버 방어 계층 |
| 5 | 메시지 유실 | Pub/Sub fire-and-forget | 시퀀스 + 풀 스테이트 싱크 | 유실 감지 + 복구 메커니즘 |
| 6 | 순서 역전 | 멀티스레드 처리 순서 꼬임 | 방 단위 액터 모델 | WAS 내부 동시성 제어 |
| 7 | 분산 스케줄링 | 타이머 소멸/중복/유실 | WAS 메모리 → Keyspace → Sorted Set + 폴링 | Redis 스케줄링 계층 추가 |
| 8 | 중복 요청 | 재전송으로 이중 처리 | 멱등성 키 | Lua에 중복 검증 추가 |
| 9 | 배포 | 무중단 배포 필요 | 기존 아키텍처로 자연스럽게 지원 | 배포 절차 확립 |

## 핵심 설계 원칙 (시나리오를 통해 도출)

1. **SSOT는 Redis에 둔다** → 서버 장애, 배포, 동시성 문제가 한 번에 해결됨
2. **Pub/Sub은 알림 역할만 한다** → 유실되면 SSOT에서 다시 읽으면 됨
3. **Stream/Kafka가 필요한 구조 자체가 설계 문제** → SSOT가 있으면 메시지 보관이 불필요
4. **Lua 스크립트로 원자성 확보** → 상태 변경 + 시퀀스 + 이벤트 발행 + 스케줄 등록
5. **액터 모델로 WAS 내부 순서 보장** → 방 단위 격리, 방 간 병렬
6. **풀 스테이트 싱크로 복구** → 어떤 장애든 "최신 상태 통째로 가져오기"
7. **pull > push (스케줄링)** → push는 유실 시 복구 불가, pull은 데이터가 남아있음
8. **클라이언트도 방어적으로 설계** → 시퀀스 갭 감지, 멱등성 키, 지수 백오프

## 면접 스토리라인

> "서비스를 스케일 아웃하면서 각 단계에서 발생하는 문제를 직접 재현하고 해결하며
> 아키텍처를 발전시켰습니다.
>
> 처음에는 Sticky Session으로 해결했지만,
> 서버 장애 테스트에서 방이 통째로 소멸하는 문제를 확인하고 이벤트 전파가 필요하다는 결론을 냈습니다.
>
> 메시지 브로커를 선택하기 전에 **'SSOT를 어디에 둘 것인가'를 먼저 결정**해야 한다는 것을 깨달았습니다.
> Redis를 SSOT로 두면 서버 장애 시 복구가 '최신 상태 읽기' 한 번이면 끝나고,
> 메시지 보관이 불필요해지면서 Stream이나 Kafka의 핵심 강점이 오히려 관리 비용이 됩니다.
> **'메시지 보관이 필요한 구조 자체가 SSOT 설계 문제'**라는 인사이트가 이 과정에서 나왔습니다.
>
> 스케줄링도 비슷한 여정을 거쳤습니다.
> WAS 메모리 타이머는 서버와 함께 죽고,
> Redis Keyspace Notification은 Pub/Sub 기반이라 유실 가능하고 모든 WAS가 수신해서 중복 실행됩니다.
> 결국 **Sorted Set + 폴링으로 전환**했는데, pull 모델이라 데이터가 남아있어 유실이 없고,
> Lua 원자적 연산으로 중복도 방지됩니다.
> 이미 사용하던 'Redis SSOT + Lua' 패턴과 일관되는 해결이었습니다.
>
> 이후 Pub/Sub 유실(시퀀스 + 풀 스테이트 싱크), 순서 역전(액터 모델),
> thundering herd(jitter + request coalescing), 중복 요청(멱등성 키)까지 해결하며
> **무중단 배포가 가능한 분산 실시간 게임 아키텍처**를 완성했습니다."
