첫 번째 시도 스레드 수 증가 — 개선 미비

가설

  • Inbound에서 유일하게 다른 점: Redis Stream XADD로 메시지 발행 (I/O 포함)
  • I/O 작업이 있으니 스레드를 늘리면 동시 처리량이 올라갈 것이라 판단
  • 스레드를 32 → 200개까지 늘려서 실험

배운 점: 스레드 증가가 해결책이 아닌 이유

  • 스레드를 늘릴수록 이 비용이 스레드 수에 비례하여 누적
  • 처리량 증가분을 깨우기/재우기 비용이 상쇄하여 개선 효율이 극히 낮음
03

원인 분석 RedisTemplate의 Blocking I/O

Inbound vs Outbound 처리 흐름 비교

[Inbound 흐름] WebSocket 메시지 수신 → Inbound Thread에서 처리 → Redis Stream XADD (Blocking I/O) ← park 진입 → Redis 응답 대기 (1~2ms) → unpark → 컨텍스트 스위칭 → 스레드 반환 [Outbound 흐름] Redis Stream Consumer (별도 백그라운드 스레드) → 비즈니스 로직 처리 → WebSocket 전송 (비동기) → 즉시 반환 ← park/unpark 없음

근본 원인

  • 핵심 차이: Inbound에만 Redis Stream XADD라는 Blocking I/O가 존재
  • RedisTemplate은 내부적으로 Lettuce의 동기 API(sync())를 사용
  • 이 API는 async().get()을 호출하여 호출 스레드를 블로킹
  • 매 요청마다 Inbound 스레드가 I/O 완료까지 park → 응답 수신 후 unpark → CS 발생
  • 스레드를 늘려도 이 사이클 자체가 제거되지 않으므로 근본적 해결이 안 됨
04

해결 방법 분석

방안 1. Virtual Thread

  • 기존 블로킹 코드 그대로 사용, carrier thread 자동 양보
  • Java 21+에서 지원, 코드 변경 최소
Virtual Thread를 선택하지 않은 이유
  • 핀닝(Pinning): Lettuce 내부 Netty가 synchronized 블록 사용 → Virtual Thread가 carrier thread를 점유하여 핀닝 발생 가능
  • 모니터링: 기존 스레드 풀 메트릭(executor_pool_size_threads)으로 계측 불가 → 별도 커스텀 메트릭 필요
  • Redisson 호환성: 분산 락에 사용 중인 Redisson도 synchronized 사용 → 핀닝 위험

방안 2. Lettuce Non-blocking API (채택)

  • Lettuce는 이미 Netty 기반 비동기 아키텍처로 설계되어 있음
  • RedisTemplate이 이를 동기로 래핑하여 사용하고 있었을 뿐
  • 네이티브 비동기 API를 직접 사용하면 park/unpark 사이클 자체가 제거됨
장점
  • 기존 Lettuce 인프라 그대로 활용
  • Inbound 스레드가 순수 CPU 작업만 수행
  • park/unpark + CS 사이클 제거
  • 핀닝 위험 없음
트레이드오프
  • 에러 처리가 콜백 기반
  • 발행 실패 시 동기적 재시도 어려움
05

해결 Lettuce EventLoop 활용

Before (Blocking)

// RedisTemplate 내부: Lettuce sync API → async().get() → 호출 스레드 블로킹 stringRedisTemplate.opsForStream().add(record, xAddOptions);

After (Non-blocking)

// Lettuce native async API → Netty EventLoop에서 I/O 처리, 호출 스레드 즉시 반환 asyncCommands.xadd(streamKey, xAddArgs, "payload", eventJson) .whenComplete((messageId, throwable) -> { if (throwable != null) { log.error("발송 실패: streamKey={}", streamKey, throwable); } });

동작 방식 변화

[Before] Inbound Thread → serialize → XADD → [1~2ms park 대기] → unpark → CS → 반환 [After] Inbound Thread → serialize → asyncCommands.xadd() → [즉시 반환, park 없음] Netty EventLoop → Redis 전송 → 응답 수신 → 콜백 실행
  • Inbound 스레드가 I/O를 전혀 하지 않음 → park/unpark 사이클 제거
  • I/O는 Lettuce의 Netty EventLoop 스레드가 전담
  • Inbound 스레드는 순수 CPU 작업(역직렬화, 검증, 직렬화)만 수행

핵심 인사이트
  • Blocking 200T: 200개 중 75개만 Active, 나머지는 park 상태 → 깨우기/재우기 비용만 발생
  • Non-blocking 16T: 16개 중 15개 Active, I/O 대기 없이 전부 CPU 작업에 활용
  • 적은 스레드로 더 높은 성능 → I/O 대기 제거 + 컨텍스트 스위칭 감소의 복합 효과
최종 결론
  • RedisTemplate의 Blocking I/O가 매 요청마다 발생시키는 park/unpark + CS 사이클을 제거
  • Lettuce의 비동기 아키텍처를 활용하여 I/O를 EventLoop에 위임
  • 스레드 수를 절반(32 → 16)으로 줄이면서도 Inbound p95 레이턴시를 3배 개선
